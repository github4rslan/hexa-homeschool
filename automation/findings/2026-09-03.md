## Bugs (Critical → Low)

- [x] **B1 · Critical · Rapid double/triple-tap on "Check answer" during a mastery check can over-score the attempt and wrongly trigger the reteach screen for a child who answered everything correctly** — `src/components/child/practice-player.tsx:914-1039`, `src/lib/engine/remediation.ts:15-22`
  - Repro / evidence: as Ivy, `maths_geometry` Mastery check 1, Q1 ("Two angles lie on a straight line...") — selected the correct option, then (per the brief's rapid-input test) fired `Check answer`.click() three times synchronously via `browser_evaluate`. UI settled once, visually correct ("Brilliant! 🎉"), no console error. Answered Q2 and Q3 correctly with single clicks. On "Finish", instead of the certificate screen, landed on **"Let's look at this another way"** with the text **"You got 5 out of 3. That shows us exactly what to practise next."** — a mathematically impossible score (5 out of a 3-question set) and a reteach screen for an attempt that was, in reality, 3/3 correct. Screenshot: `.playwright-mcp/scout-mastery-overscore-bug.png` (gitignored path, not committed). Recovered cleanly on the next attempt ("Try a fresh check" → 3/3 single-clicked → "Still mastered!" — EPIC 13's certified-date-doesn't-move guarantee held, and the corrupted attempt did not leak into `countCertified`/admin activity, which is the only reason this wasn't worse).
  - Root cause (two-part, confirmed by reading the code, not just guessing from the symptom):
    1. **The over-score.** `check()` (line 917) guards re-entrancy with `checkingRef.current`, but for any non-`fill_blank` interaction (mcq/tap_reveal/drag_drop — no `await` on that path) the whole function runs synchronously to completion, so the ref is set `true` and reset back to `false` in the same synchronous tick. Three synchronous `.click()` calls in one JS turn therefore all pass the `checkingRef` guard. Worse, `runCheckCore()`'s own guard (`if (!ready || !question || revealed || outcome === "correct") return;`, line 946) reads **React state** (`revealed`, `outcome`) that hasn't re-rendered yet within that same synchronous burst, so it doesn't block the 2nd/3rd call either. The scoring guard `if (!scoredThis) { setScore((s) => s + 1); setScoredThis(true); }` (lines 955-958) reads the same stale `scoredThis` (still `false`) on all three calls, so `setScore((s) => s + 1)` — a functional updater, so React does NOT dedupe it — gets queued three times, giving `score += 3` for one logical answer instead of `+1`.
    2. **The false reteach.** `decideRemediation` (`lib/engine/remediation.ts:20`) is `if (input.total > 0 && input.score === input.total) return "certified";` — a **strict equality** check with no defensive clamp. A legitimately-inflated `score` (5) no longer equals `total` (3), so a child who got every question right is routed to `"remediate"` instead of `"certified"`. The exact triple-click on Q1 (score 3) plus two further correct single-click answers (2 more) reproduces `5` precisely, matching the observed "5 out of 3" text exactly.
  - Fix (two parts, both small and testable):
    1. In `practice-player.tsx`, make the re-entrancy/already-answered guard a **ref**, checked and set at the very top of `runCheckCore()` **before** any state setter runs (e.g. `const settledRef = useRef(false)`, reset it only when a new question mounts/`resetStepState()` runs, not in a `finally`). This closes the race for every interaction type, not just `fill_blank`.
    2. Defensively harden `decideRemediation` in `lib/engine/remediation.ts` to treat `score >= total` as `"certified"` (clamp or `>=` instead of `===`), so any future scoring anomaly degrades to "pass" rather than a demoralising false "fail" — this is the cheap, high-value belt-and-braces fix regardless of whether (1) fully closes the race. Add a unit test for `decideRemediation({ score: 5, total: 3, attempt: 1 })` returning `"certified"`, plus a `practice-player` regression note in `PRACTICE-PLAYER.md`/inline comment referencing this bug.
  - Risk: Low-medium. The re-entrancy fix touches the core answer-check path used by every lesson in the product, so it needs the full gate (type-check, all tests, build) plus a live re-drive of at least one mcq, one fill_blank, one tap_reveal and one drag_drop question (correct AND wrong) to confirm no regression, per this run's own interaction-type coverage. The `decideRemediation` clamp is pure and low-risk on its own but changes exam-readiness-adjacent logic — re-run `mock-exam`/`remediation` tests after.

- [x] **B2 · High (EPIC 19 slice, perf) · `getActiveChild()` still issues its own serial DB round-trip on `/dashboard`, `/schedule` and `/learn`, even though the sibling child list already fetched on the same page contains everything needed to resolve it locally** — `src/lib/db/repo.ts:412-421`, `src/app/(dashboard)/dashboard/page.tsx:210`, `src/app/(dashboard)/schedule/page.tsx:43`, `src/app/(child)/learn/page.tsx:54`
  - Repro / evidence: this run first **live re-measured** 2026-09-02's B1 perf fix (which shipped and landed — confirmed via `grep -c Promise.all` showing the batching is live) using `performance.getEntriesByType('navigation')[0]`, `responseEnd - responseStart`, as the SMOKE parent, fresh `browser_navigate` loads each time: `/dashboard` **1,895ms** then **2,312ms** (down from the pre-fix 7,026ms — a real, large improvement, thank you Mechanic), `/schedule` **4,470ms** then **2,069ms** (noisier — see below), `/learn` **5,131ms**. All three are still well above the fix's own stated ~1.5s target (`/settings`'s clean baseline). Reading the code to root-cause the residual gap: `getActiveChild(parentId, preferredChildId)` (`repo.ts:412`) does `getChildById()` (an ownership-checked `findOne`) or `latestChild()` (a sorted `findOne`) — **a full extra Mongo round-trip** — and on all three pages this call sits as its own **serial `await`**, positioned BETWEEN two `Promise.all` batches rather than inside either of them. On `dashboard/page.tsx` specifically, this is doubly wasteful: `listChildren(parentId)` (the exact same collection, same parent, same rows) is *already* fetched in the FIRST batch (line 173's `Promise.all`) as `kids`, one line before `getActiveChild` reruns an equivalent query against the same data.
  - Root cause: `getChildById(parentId, childId)` = "find the doc in `kids` whose `_id` matches" and `latestChild(parentId)` = "the most-recently-created doc" = `kids` sorted by `created_at` (which `listChildren` already returns ascending, confirmed by reading `repo.ts:369-373` — `.sort({ created_at: 1 })`), so `latestChild` is simply the **last element** of the already-fetched `kids` array. Both branches of `getActiveChild` are fully derivable in pure JS from data the page already has (or can fetch in the same batch), with zero need for a second round-trip.
  - Fix: add a pure helper, e.g. `resolveActiveChild(children: ChildDoc[], preferredId?: string): ChildDoc | null` in `lib/db/repo.ts` or a sibling pure module (`return children.find(c => c._id!.toHexString() === preferredId) ?? children.at(-1) ?? null`, matching `getChildById`'s ownership-is-implicit-in-the-list semantics and `latestChild`'s "last in ascending `created_at`" order exactly) — unit-testable in isolation. Then on each page: fetch `listChildren`/siblings **in the same first batch** as the id-resolution inputs (dashboard already does; schedule and learn need `listChildren` pulled forward into their first `Promise.all` instead of being fetched later or not at all), call the new pure resolver instead of `await getActiveChild(...)`, and keep `getActiveChild` itself for any other call site that doesn't already have the sibling list in scope (no need to delete it, just stop using it where a cheaper local resolution is available). This removes one full serial Mongo round-trip from all three of the highest-traffic pages in the product.
  - Risk: Low — pure, unit-testable resolver; the two branches being replaced are simple filters over already-owned data (ownership was already established by `listChildren(parentId)`'s own query, so no ownership check is weakened). Re-measure all three pages with the same Performance-API technique after shipping and update `automation/backlog.md` EPIC 19 with the new numbers.
