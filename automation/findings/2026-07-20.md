## Bugs (Critical → Low)

- [ ] **B1 · HIGH · "Forgot password?" is a dead link — 404 + console error, and there is no password-reset flow at all** — `src/app/(auth)/login/page.tsx:56`
  - Repro / evidence: load `https://edway.uk/login` → the RSC prefetch of `/forgot-password` throws `Failed to load resource: 404` in the console (the one console error present on every page of the site, signed in or out); clicking the link lands the user on a 404. `curl -sI https://www.edway.uk/forgot-password` → `404`; `/reset-password` → `404`. No route exists under `src/app/(auth)/` for either.
  - Root cause: the login form links to `/forgot-password`, and `lib/monitoring/sentry-shared.ts:36` even route-tags it, but the page/flow was never built.
  - Fix (bug-minimum): stop the dead end. The proper fix is to build the flow — see **F1**, which supersedes this. If only B1 is selected, at minimum remove/disable the link so there's no 404 and no console error.
  - Risk: none for removing the link; building the flow is F1's risk.

- [ ] **B4 · MEDIUM · Child mode: the daily Maths quest is a silent dead-end — tapping it bounces back to `/learn` with no message** — `src/app/(child)/learn/lesson/page.tsx:120`, `src/app/(child)/learn/page.tsx:107`
  - Repro / evidence: sign in as the test parent, enter child mode as the active child (Sam Test), and tap the **Maths** quest (`/learn/lesson?topic=maths_number_fractions`). The lesson page immediately server-redirects back to `/learn` — the child sees the home screen again, no lesson, no explanation. The **Science** quest (`/learn/lesson?topic=sci_ks3_cells`) loads a real lesson from the same screen, so it's topic-specific, not a global outage. The quest card still advertises progress ("0/10"), so it looks tappable.
  - Root cause: `/learn` builds each quest's `href` from the planned/first-in-band topic tag **without checking that the topic actually has playable questions**; `lesson/page.tsx:120-122` then does `redirect("/learn")` when `getQuestions()` returns empty (the topic exists but has no questions matching `{ topicTag, keyStage: topicDoc.key_stage ?? 4 }` — either none seeded or a key-stage filter mismatch). The redirect is silent — a dead end, which the recent "no dead ends" child-simple work was meant to eliminate.
  - Fix: (1) in `lesson/page.tsx`, replace the bare `redirect("/learn")` on the empty-questions branch with a calm "this quest isn't ready yet — try another" `FocusFrame` screen (mirrors the `HandoffPause` pattern), so a child is never bounced without a word; (2) in `/learn`, filter quests to topics that have questions (or mark a question-less topic as a non-startable "coming soon" card) so it's never presented as tappable; (3) investigate the data/query root cause — why `maths_number_fractions` resolves to zero questions while `sci_ks3_cells` doesn't (missing seed vs. `key_stage` filter drift in `getQuestions`).
  - Risk: keep the child-safety bar — the "not ready" screen is static human-authored copy (no AI), so no checker/distress implications; the `/learn` filter must not hide a subject entirely if all its in-band topics lack questions (fall back to the next available topic).

- [ ] **B5 · MEDIUM · Role-blind routing: tutor/admin sessions land on the parent `/dashboard`, and parent-only routes aren't role-gated** — `src/lib/auth/middleware.ts:44`, `src/app/(dashboard)/**` layout
  - Repro / evidence: sign in as the tutor account (`scout-tutor@example.com`) — you land correctly on `/tutor`. Now visit `/login` (or the site root): the middleware bounces every authenticated user to `/dashboard` regardless of role, so the tutor lands on the **parent** dashboard and sees the parent onboarding ("Let's set up your first child"). `/tutor` (`(tutor)/tutor/layout.tsx:21`) and `/admin` both correctly gate by role and redirect non-members to `/dashboard`, but `/dashboard`, `/schedule`, `/settings`, `/portfolio`, `/tutoring` only assert "signed in" — no check that the account is actually a parent — so a tutor/admin can load them.
  - Root cause: `updateSession()` hard-redirects `isAuthRoute` hits to `/dashboard` (line 44-48) with no role awareness (Edge middleware can't read the DB, so role routing must happen in the layout/action layer); the parent route group has no `resolveRole`-based guard equivalent to the tutor/admin layouts.
  - Fix: after a successful sign-in and on the `/login` bounce, send tutors to `/tutor` and staff to `/admin` (the post-auth `redirect` in `login/actions.ts` already knows the role — reuse it so the "already signed in" path is role-aware too); and add a parent-role assertion to the `(dashboard)` layout so a tutor/admin visiting a parent route is redirected to their own home rather than shown an empty parent shell. No cross-family data leaks today (the silo holds — a tutor has no children), so this is role hygiene + correct routing, not a breach.
  - Risk: don't lock a legitimate parent-who-is-also-staff out of the dashboard — gate on "can read parent surface", not "is not staff".

- [ ] **B2 · LOW · Homepage stat advertises "5%" Meta Checker audit coverage (should be 100%)** — `src/components/marketing/stats-strip.tsx:18`
  - Repro / evidence: scroll the homepage `#stats` strip; the third counter animates to `5%` under the label "Continuous Meta Checker audit coverage". The whole site's pitch is that *every* AI output is checked, so "5% coverage" actively undercuts the core trust claim. Verified live (counter settles on `5%`).
  - Root cause: `{ value: 5, suffix: "%", label: "Continuous Meta Checker audit coverage" }` — almost certainly meant `100`.
  - Fix: set `value: 100`.
  - Risk: none (marketing copy only).

- [ ] **B3 · LOW · Login ignores its own `?redirect=` param — protected-page redirects always dump the user on `/dashboard`** — `src/app/(auth)/login/actions.ts:119`, `src/app/(auth)/login/page.tsx:16`
  - Repro / evidence: `settings/actions.ts:31` sends signed-out parents to `/login?redirect=/settings`; the login page types `searchParams.redirect` but never renders it into the form, and `login()` hard-codes the post-auth destination (`/tutor` | `/admin` | `/dashboard`). The intended destination is silently dropped. (Closely related to B5 — both are post-auth routing gaps.)
  - Root cause: `redirect` is read into the page's prop type but never forwarded (no hidden input) and never consulted by the action.
  - Fix: render a hidden `<input name="redirect">` from the (validated, local-path-only) searchParam, and in `login()` prefer a `redirect` form value that starts with `/` and isn't `//` — otherwise fall back to the role default. Keep the open-redirect guard.
  - Risk: must reject non-local targets to avoid an open redirect; low.

- [ ] **B6 · LOW · Settings password/PIN forms trip Chrome DOM warnings (no username field, no `autocomplete`) — weakens password-manager + a11y support** — `src/app/(dashboard)/settings/**` (password + PIN forms)
  - Repro / evidence: on `/settings`, DevTools logs (verbose) `Password forms should have (optionally hidden) username fields for accessibility` (×2) and `Input elements should have autocomplete attributes (suggested: "new-password")` (×2). The change-password and set-PIN forms have password inputs with no associated username field and no `autocomplete` hints, so password managers can't reliably offer/save credentials and screen-reader context is weaker.
  - Root cause: the forms omit a hidden `username`/email field and `autocomplete="current-password"` / `"new-password"` on the inputs.
  - Fix: add a visually-hidden `<input type="text" name="username" autocomplete="username">` prefilled with the signed-in email, and set `autocomplete="current-password"` on the current-password field and `autocomplete="new-password"` on the new-password field. Same treatment for the PIN form where applicable.
  - Risk: none material; purely additive attributes.

- [ ] **B7 · LOW · Billing/plan copy state slips for active subscribers + admin pluralization** — `src/app/(dashboard)/settings/**` (billing card), `src/app/(admin)/admin/finance/**`
  - Repro / evidence: on `/settings`, the test parent's billing card correctly shows "Edway Complete" / "active", yet directly under it renders "Choose a plan" → `/pricing` and "14-day free trial. Cancel anytime." — trial/upsell copy shown to someone already subscribed, with no "Manage billing" (Stripe portal) link. (In this environment Stripe is unconfigured — finance page confirms `STRIPE_SECRET_KEY` is missing — so the portal link is hidden; but the trial line is wrong regardless of Stripe state.) Separately, `/admin/finance` "Subscription mix" prints "1 accounts" (×2) — missing singular pluralization.
  - Root cause: the billing card doesn't branch its CTA/subtext on `billing_status === "active"`; the finance list interpolates a count without a plural helper.
  - Fix: when the account is active/paying, show plan name + renewal + (when Stripe is live) a "Manage billing" portal link, and drop the "14-day free trial" line; add a simple `count === 1 ? "account" : "accounts"` helper in the finance list.
  - Risk: none (copy/conditional only).

## Features & upgrades (High value → Low)

- [ ] **F1 · security+feature · Build the password-reset flow** (size: M)
  - The win: closes B1 and ships a table-stakes account-recovery path. Right now a parent who forgets their password is permanently locked out of the account that gates their children's data.
  - Change: add `(auth)/forgot-password/page.tsx` (email input → always-generic success message, no account enumeration) and `(auth)/reset-password/page.tsx` (token + new password). Reuse the existing signed-token pattern in `lib/email/verification.ts` (jose HS256, short TTL) and a new Brevo template in `lib/email/templates.ts`. On successful reset, hash with `lib/auth/password.ts` and **bump `ParentDoc.token_version`** to invalidate existing sessions ("sign out everywhere" already keys off it). Rate-limit both the request and the submit via `lib/rate-limit.ts` (per-IP + per-email, mirroring `login/actions.ts`). Graceful-degrade: with Brevo unset, show the same generic screen (no email, no crash), consistent with the codebase's "unset provider = no-op" rule.
  - Risk: token replay (bind token to a `password_hash`/`token_version` snapshot so it's single-use); enumeration (identical response whether or not the email exists).

- [ ] **F2 · security+stack · Patch the 5 audit CVEs and move Tailwind off the beta** (size: S)
  - The win: clears `npm audit` (dompurify ALLOWED_ATTR pollution, js-yaml DoS, esbuild dev-server file read via `tsx`, postcss `</style>` XSS via Next's bundled copy) and gets production off `tailwindcss@4.0.0-beta.8` / `@tailwindcss/postcss@4.0.0-beta.8` onto stable Tailwind 4.x. Shipping a UI framework beta to prod is avoidable risk.
  - Change: `npm audit fix` for the non-breaking ones; bump `tailwindcss` + `@tailwindcss/postcss` to the latest stable 4.x and re-run `npm run build` + a visual pass (Tailwind 4 stable dropped some beta-era config quirks). Consider dropping `autoprefixer` if the Tailwind 4 pipeline makes it redundant. Leave `next`'s bundled postcss alone unless the Next bump is intentional.
  - Risk: Tailwind beta→stable can shift a few utility/config behaviours — build + eyeball marketing + dashboard + child surfaces before pushing.

- [ ] **F3 · feature · SEND-aware reading supports in child mode** (size: M)
  - The win: `ChildDoc` already carries SEND indicators but nothing acts on them. A dyslexia-friendly font toggle, an adjustable text-size control, and a reading-ruler / line-focus overlay in the child lesson would be a genuine accessibility win and a strong differentiator for exactly the families Edway targets (e.g. Ivy, the primary/SEND profile). Fully Children's-Code aligned (no tracking, child-controlled).
  - Change: extend the child "My stuff" personalisation (alongside `voice_id`/`accent`/`narration_autoplay`) with `reading_font` + `text_scale` + `reading_ruler` on `ChildDoc` (repo-layer, ownership-checked); thread through `FocusFrame` / `interaction.tsx` / `DailyFlow` the same way `accent` already threads. Default off; persists per child. Respect `prefers-reduced-motion` for the ruler.
  - Risk: keep new controls inside the ≥64px `.child-touch` + WCAG-AA bar; no new free-text surface, so no distress-gate implications.

- [ ] **F8 · ui · Consistent, always-visible child switcher on `/schedule` + `/tutoring` (match `/portfolio`)** (size: S/M)
  - The win: the test family has 3 children, but `/schedule` and `/tutoring` silently act on the "active child" — a concept only changeable from a control buried inside the hamburger menu, with no indication on the page of *which* child you're planning/booking for. `/portfolio` already has a clean inline child `<select>`; the other per-child surfaces don't. For a multi-child household this is a real "wait, whose plan am I editing?" trap. Making the active child obvious and switchable inline (and showing the child's name in the page header) is a small, high-frequency UX win.
  - Change: add the same inline child selector `/portfolio` uses to the `/schedule` and `/tutoring` page headers (repo-layer, ownership-checked list of the parent's children), defaulting to the active child and updating `readActiveChildId`/the active-child cookie on change; surface the selected child's name in each page's `<h1>`/intro. Optionally promote the switcher into the dashboard header so it's one tap everywhere.
  - Risk: keep every child lookup ownership-checked through `repo.ts`; don't let a stale active-child cookie point at a deleted child (fall back to the first owned child).

- [ ] **F4 · security · TOTP authenticator-app 2FA** (size: M)
  - The win: 2FA today is email-code only (`login/actions.ts`), which is only as strong as the parent's inbox. Adding TOTP (authenticator app) hardens the accounts that gate children's data and is a credible trust-page bullet.
  - Change: add `otplib` (or a jose/`crypto`-based HOTP), QR enrolment in `/settings` (store an encrypted `totp_secret` + `totp_enabled` on `ParentDoc`), and a verify step in the sign-in flow parallel to the existing `two_factor_enabled` email branch. Keep email-code as a fallback. Recovery codes generated at enrolment.
  - Risk: secret storage must be encrypted at rest (not plain in Mongo); clock-skew window; don't lock out email-2FA users mid-migration.

- [x] **F5 · feature · Installable, offline-resilient PWA** (size: M/L)
  - The win: Edway is a *daily* learning app; `src/app/manifest.ts` already exists but there's no service worker, so no install prompt and no offline resilience. A cached app shell + offline lesson-resume (the interactive flow already autosaves to `localStorage` + `lesson_progress`) means a dropped connection mid-lesson doesn't strand a child.
  - Change: add a service worker (hand-rolled or `@serwist/next`) caching the static shell + last lesson payload + cached TTS clips; wire an install prompt in the parent app. CSP already allows `worker-src 'self' blob:`. Keep it out of any analytics path and never cache child PII.
  - Risk: SW cache-invalidation on deploy (version the cache); make sure the distress gate + checker still run server-side (never serve AI from cache to a child).

- [x] **F6 · feature · Parent weekly audio recap** (size: S/M)
  - The win: reuse the ElevenLabs TTS path (`/api/tts`, Cloudinary-cached) to turn the already-deterministic weekly summary (`lib/engine/weekly-summary.ts`) into a ~60-second narrated recap for busy parents — attached to the weekly digest email and shown on the dashboard. Novel, on-mission, reuses existing infra, exposes zero child PII beyond what the digest already contains.
  - Change: generate the recap text from `weekly-summary.ts`, synthesize via the existing TTS cache keyed by text hash, store the Cloudinary URL on the digest, surface a play control in `components/dashboard/` and a link in `email/`. Respect `weekly_digest_opt_out`.
  - Risk: TTS spend — cache aggressively by content hash (already the pattern) and gate to opted-in parents; degrade silently when ElevenLabs is unset.

- [ ] **F9 · feature · Build out the tutor workspace** (size: M/L)
  - The win: the `/tutor` surface is currently a single stat strip + an empty "No sessions assigned yet" list (video = Jitsi). Its own copy promises "Join scheduled rooms, message families, and complete notes after tutoring," but the family-messaging and post-session-notes tooling isn't there to exercise. Since human tutoring is the paid escalation path when AI reaches its limit (and `/tutoring` lets parents request sessions), a real tutor console — assignment queue, session notes written back to the child's record, a scoped family-message thread, availability — turns a stub into a working leg of the product.
  - Change: extend the `(tutor)` route group with a session-detail workspace (notes editor persisting to a `tutor_session_notes`/booking doc via repo-layer, ownership/role-checked), a scoped message thread between tutor and the requesting parent, and an availability setting; surface tutor notes back on the child's dashboard/portfolio evidence. Keep everything role-gated (`tutor.session.*` in the rbac matrix) and out of the `(child)` surface.
  - Risk: strict data-silo — a tutor must only ever see the specific child/booking assigned to them (new repo functions with explicit assignment checks, never a broad `getCollection`); notes are safeguarding-relevant, so audit-log writes and keep them out of any analytics path.

- [x] **F7 · ui · Honour `prefers-reduced-motion` in marketing motion** (size: S)
  - The win: child components already respect reduced motion, but the marketing `CountUp` (`src/components/fx/count-up.tsx`) drives numbers via `requestAnimationFrame`, which CSS `prefers-reduced-motion` can't stop, and the `whileInView` fades in `stats-strip.tsx` aren't gated. WCAG 2.3.3 — vestibular-safety gap on the highest-traffic pages.
  - Change: in `CountUp`, read framer-motion's `useReducedMotion()` and jump straight to the final formatted value when reduced motion is set; gate the `initial/whileInView` offsets similarly. Small, isolated.
  - Risk: none material.
