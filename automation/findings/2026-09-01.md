## Bugs (Critical → Low)

- [ ] **B1 · Critical · Every authenticated data-heavy page (`/dashboard`, `/schedule`, `/learn`) blocks full page load for 4–8 SECONDS on every single visit — a serial waterfall of independent DB round-trips inside one Server Component, not a network or DB-capacity problem** — `src/app/(dashboard)/dashboard/page.tsx`, `src/app/(dashboard)/schedule/page.tsx`, `src/app/(child)/learn/page.tsx`
  - Repro / evidence: measured via `performance.getEntriesByType('navigation')[0]` (`responseStart` = when the first response byte/headers arrive; `responseEnd` = when the full HTML body finishes streaming; the gap between them is server-side think-time, not client render time) on **six separate fresh `browser_navigate` loads**, all as the SMOKE parent:
    - `/dashboard`: `responseStart` 481ms → `responseEnd` **7362ms** (gap **6.9s**); re-measured a second time: `responseStart` 654ms → `responseEnd` **8431ms** (gap **7.8s**).
    - `/schedule`: `responseStart` 679ms → `responseEnd` **8109ms** (gap **7.4s**, this load also triggered first-of-week schedule generation for a child with no plan yet).
    - `/learn` (child hub): `responseStart` 485ms → `responseEnd` **4594ms** (gap **4.1s**); re-measured again: gap **4.1s**.
    - Baselines confirm this is NOT general network/DB slowness: `/pricing` (static marketing, prerendered): gap **3ms**. `/settings` (authenticated but account-only data, no cross-child aggregation): gap **620ms**. `/api/health` (does a live DB ping): **0.7–0.9s total** via `curl` × 3. `/admin` (aggregate platform stats, but from a genuinely tiny dataset — 12 parents, 13 children): gap **37ms**.
    - A parent's very FIRST view after logging in — the dashboard — is blank/loading for 7+ seconds on every visit, not just a cold start.
  - Root cause (confirmed by reading the actual page components, not just measured): each of these three Server Components makes 12–19 `await` calls (`grep -c "await "`: dashboard 19, learn 15, schedule 10), and the majority of them are **fully independent reads awaited one after another** instead of batched with `Promise.all`. Concretely in `dashboard/page.tsx`: `logs` (line 192), `certifiedThisWeek` (205), `escalations` (208), `feedItems` (214), `complianceReady` (226), `dismissed` (231), `fbContext` (280) and `masteredToday` (286) are ALL independent of each other (none consumes another's result) yet run as eight back-to-back sequential MongoDB Atlas round-trips; the per-child loop inside the existing `Promise.all` (163–187) itself does two more SEQUENTIAL awaits per child (`countCertified` then `latestEvaluationsBySubject`, could be `Promise.all([...])`). `learn/page.tsx` has an even longer unbroken chain: lines 57, 58, 63, 64, 65, 66, 67, 68, 72, 82, 94 are eleven consecutive independent `await`s before the code finally batches quest resolution at line 110. `schedule/page.tsx`'s own top-level awaits are fewer, but its heaviest call, `getOrCreateWeeklySchedule` → `buildScheduleItems` (`src/lib/db/repo.ts`), does its own serial chain (child lookup, competence list, `latestEvaluationsBySubject`, then `topicsCol.find({})` for every curriculum topic) whenever a child doesn't yet have a schedule for the current week — exactly what happened on the slowest `/schedule` measurement. At realistic Vercel-serverless-to-Atlas round-trip latency (a few hundred ms each, confirmed by the 300–600ms `responseStart` figures seen everywhere), 12–19 SEQUENTIAL round-trips is the textbook arithmetic behind a 4–8 second wait: this is the classic Server Component "await waterfall" anti-pattern, not a scaling/capacity issue.
  - Fix: group every set of independent, sibling `await`s into a single `Promise.all([...])` in each of the three files (the pattern the code ALREADY uses correctly for the per-child `children` array and `todayCards` — extend that same pattern to the rest of the function body). For `dashboard/page.tsx` this alone should cut ~8 sequential calls down to ~2–3 parallel batches (one for the calls that need `childIds`, one for the calls that only need `parentId`/`activeChild`). Do the same audit inside `buildScheduleItems` in `repo.ts` for the once-a-week generation path. This is a pure reordering of already-correct, already-tested logic — no query behaviour changes, so it's low-risk to ship, but touches three of the most-visited pages in the app, so re-verify with the same Performance-API measurement technique after the fix (target: `/dashboard` and `/learn` gaps under ~1.5s, matching `/settings`'s baseline).
  - Risk: Low functionally (reordering independent reads is safe by definition — nothing depends on execution order here), but this is the single highest-traffic surface in the product, so run the full test suite plus a live Playwright re-measurement on all three pages before calling it done, not just the gate.
