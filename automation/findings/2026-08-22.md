## Bugs (Critical → Low)

- [x] **B1 · Critical · A GCSE algebra "collect like terms" practice question shows a completely wrong number-line figure that contradicts the correct answer** — `src/lib/child/math-visual.ts:213-241` (`deriveNumberLine`), dispatch order `src/lib/child/math-visual.ts:558-565`
  - Repro / evidence: as Ivy (KS4 Maths, Linear Algebra), practice question "Simplify 5x + 2 − 3x." (correct answer `2x + 2`, index 0) renders a derived figure with alt text **"A number line: start at 2, move 3 left to land on -1."** — a completely different, wrong piece of arithmetic that has nothing to do with the actual answer. Screenshot: `.playwright-mcp/wrong-numberline-algebra.png` shows the number-line arc from 2 to -1 sitting directly above the correctly-highlighted `2x + 2` option. Confirmed live by walking the exact question end to end (answered correctly, celebration fired, figure stayed visibly wrong throughout).
  - Root cause: `deriveNumberLine`'s regex `/\(?\s*(-?\d+)\s*\)?\s*([+-])\s*\(?\s*(-?\d+)\s*\)?/` scans the **whole prompt string** for the first `number op number` substring it can find, with no check on what's immediately before/after each digit group. In `"Simplify 5x + 2 − 3x."` it matches the substring `"2 − 3"` (skipping straight past the "5x" and ignoring that the "3" it captured is immediately followed by "x", i.e. it's actually the coefficient of `3x`, not a standalone integer). `deriveNumberLine` runs in the chain **before** `deriveAlgebraTiles` (which correctly declines this prompt because its own "collect like terms" regex requires the SAME variable to reappear immediately after the second number, and here there's an extra `+ 2 −` constant in between), so the wrong number-line wins by default instead of the prompt falling through to a nulled/generic result.
  - Fix: add a boundary guard to `deriveNumberLine` so it never matches a digit that's part of a variable term — e.g. `/(?<![a-zA-Z0-9])\(?\s*(-?\d+)\s*\)?\s*([+-])\s*\(?\s*(-?\d+)\s*\)?(?![a-zA-Z])/` (negative lookbehind before the first digit group, negative lookahead after the second). Add a unit test asserting `deriveNumberLine("Simplify 5x + 2 − 3x.")` returns `null` (and that the existing `"−3 + 7"`-style pure-arithmetic prompts still match).
  - Risk: low — the fix only makes the regex *more* conservative (fewer matches), so it can only remove wrong figures, never introduce new ones. Re-run the full `math-visual` test suite to confirm no existing passing prompt regresses to `null`.

- [x] **B2 · High · A Science-only "See the process" teaching-animation renders on an English literary-devices mastery question, because of a false-positive keyword match on the word "sound"** — `src/lib/child/teaching-animations.ts:489-524` (`deriveScience`), dispatch order `src/lib/child/teaching-animations.ts:795-810` (`normalizeTeachingAnimation`)
  - Repro / evidence: as Ivy, mastery question `"'Silently, slowly, secretly she crept.' The repeated 's' sound is:"` (English topic `eng_ks3_reading`, correct answer `alliteration`) opened a "See it" walkthrough titled **"See the process"** with intro **"Science questions often become easier when you watch the change"**, an Eddie line **"Let's follow what moves or changes"**, and a Start→Change→Result stepper whose Step-1 note reads **"Find the object, energy, force, or material in the question."** — none of which has anything to do with an English alliteration question. Screenshot: `.playwright-mcp/science-template-on-english-question.png`. Confirmed live by driving the question to a mastery-check failure (3 wrong tries) and opening the reveal.
  - Root cause: `deriveScience`'s topic-sniff regex is `/(particle|energy|force|circuit|current|voltage|cell|atom|reaction|light|sound)/i` run against `prompt + " " + explanation`. The prompt contains the ordinary English word **"sound"** (as in "the repeated 's' sound"), which the regex treats as evidence of a Science physics question. `deriveGrammar` (which runs immediately before `deriveScience` in the chain) doesn't catch this prompt first because its own keyword list (`verb|noun|adjective|sentence|comma|apostrophe|grammar`) has no literary-device vocabulary, so alliteration/onomatopoeia/rhyme-type English questions fall through past it and land on the Science deriver by accident.
  - Fix: the most robust fix is to stop keyword-sniffing raw text entirely and gate both `deriveGrammar` and `deriveScience` on the question's actual `subject` field (`"english"` / `"science"`), which is already known at the call site — `topicDoc.subject` (or `q.subject`) is available in `src/app/(child)/learn/lesson/page.tsx:102-117` where `normalizeTeachingAnimation` is called, but is currently never passed in. Add an optional `subject?: Subject` param to `normalizeTeachingAnimation`/`deriveScience`/`deriveGrammar` and short-circuit each deriver to `null` when the subject is known and doesn't match, before the keyword regex runs at all. As a cheaper interim fix, broaden `deriveGrammar`'s keyword list to include literary-device terms (`simile|metaphor|personification|alliteration|onomatopoeia|rhyme|stanza|narrator|viewpoint`) so it wins first for English content — but the subject-gate is the fix that actually closes the false-positive class, not just this one instance.
  - Risk: low-medium — touches a shared dispatch chain used by every lesson; must re-run the derive-chain unit tests and spot-check that legitimate Science prompts (e.g. "sound" questions that genuinely ARE about sound waves in Physics) still resolve to `deriveScience` once the subject param is threaded through as `"science"`.

  - Repro / evidence: read the full call path in `verifyParentPin` — it does `findParentById` → `verifyPassword(pin, parent.parent_pin_hash)` (a bcrypt compare) with **zero** call to `rateLimit()` anywhere in the function or any of its three server-action callers. Compare with `src/app/(auth)/login/actions.ts:39-48`, which gates the exact same class of check (`verifyPassword` against a bcrypt hash) behind `rateLimit(`login-ip:${ip}`, 10, 60_000)` **and** `rateLimit(`login-email:${email}`, 10, 15*60_000)`, with an explicit code comment: *"unbounded POSTs here are a credential-stuffing + bcrypt-CPU-DoS surface... Trip → the same generic message."* `forgot-password/actions.ts` applies the identical pattern to password-reset requests and submissions. The parent-PIN gate is a 4-digit PIN (only 10,000 possible values) guarding entry back into the parent's dashboard/settings/billing from child mode — the exact "shared-device, lower-trust surface" scenario the login rate-limit's own comment describes — yet it alone has no throttle. Live-verified the legitimate flow works (entered the correct PIN via `/learn/map`'s "Exit" dialog, landed on `/dashboard`); did not brute-force it live against production (that would itself be an abusive test), but the code-level absence of any `rateLimit()` call is unambiguous.
  - Fix: add the same per-IP + per-parent rate-limit pair used by `login`/`forgot-password` to `verifyParentPin` itself (so all three call sites get the protection for free) — e.g. `rateLimit(`parentpin-ip:${ip}`, 10, 60_000)` and `rateLimit(`parentpin-parent:${parentId}`, 10, 15*60_000)`, returning the existing generic `"That PIN was not recognised."` message on trip (never a distinct "too many attempts" message that would leak timing/state to a child trying to guess it). `clientIp()` from `lib/auth/client-ip.ts` is already available for reuse.
  - Risk: low — additive only, mirrors an established, tested pattern in the same codebase; the only care needed is not to lock out a *legitimate* parent who fat-fingers their own PIN a few times, so keep the same generous limits (10 per minute / 10 per 15 minutes) `login` already uses.

- [ ] **B4 · Medium · `tap_reveal` conflates "reveal a card to read it" with "select it as your final answer" — re-reading another card after choosing silently overwrites the answer** — `src/components/child/interaction.tsx:397-401` (`tap(i)`), `:356-475` (`TapReveal`)
  - Repro / evidence: the interaction's own instruction copy says *"Tap each card to read it, then choose the [answer]"* (e.g. `eng_devices`'s tap_reveal question: "Tap each card to read it, then choose the simile."), which reads as: reveal all three, THEN make a separate choice. But `tap(i)` (`interaction.tsx:397-401`) does `setFlipped(prev => new Set(prev).add(i)); setSelected(i);` on **every single tap** — there is no separate "confirm your choice" step. Live-verified: tapped Card A (revealed "The classroom was a zoo", visibly became the `chosen` (selected) card with the accent border), then tapped Card B just to read it too — Card B silently became the new `chosen`/selected answer (confirmed via the accessibility snapshot: `pressed` moved from Card A to Card B), with no warning that the earlier "answer" had been replaced. A child who does exactly what the instruction tells them (read every card, then decide) will have their answer silently become whichever card they happened to tap *last* while re-reading, not the one they actually meant to choose.
  - Fix: separate "revealed" state from "selected" state — keep `flipped` as-is (reveal never un-reveals, correct), but stop `tap(i)` from also setting `selected` on every tap. Instead, once a card is flipped, a second explicit tap on an *already-flipped* card marks it as the chosen answer (or add a lightweight "Choose this" affirmation once ≥1 card is flipped). Simpler alternative that keeps the single-tap-per-card feel: don't auto-select on first reveal — only start tracking `selected` once the child taps a card that is *already* flipped (i.e. the first tap always just reveals, a second tap on the same or a different already-revealed card commits the choice).
  - Risk: low-medium — touches the shared `TapReveal` component used by every `tap_reveal` question (both seeded: `eng_devices`, `sci_cells`); re-verify `checkTapReveal`/`answerText` in `useImperativeHandle` still read `selected` correctly after the change, and that the existing correct/wrong settle animations (gated on `celebrate = showCorrect && chosen`) still fire on the child's actual final choice.
