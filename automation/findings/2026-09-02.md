- [x] **B2 · Medium-High (NEW) · `/dashboard` never redirects to `/login` when the session is valid-but-stale (deleted account, or "sign out everywhere" token-version bump) — it silently renders the generic zero-children onboarding empty state instead** — `src/app/(dashboard)/dashboard/page.tsx:122-157`
  - Repro / evidence: discovered incidentally while cleaning up this run's disposable signup test account. Sequence: signed up + verified a fresh test parent (session cookie set, redirected to `/onboarding`) → deleted that parent's DB row directly (the same effect `deleteFamilyData`/GDPR erasure produces) → navigated to `/login` with the still-valid session cookie still attached → the app redirected straight to `/dashboard` (middleware only checks JWT signature, by design, see its own comment) → the page rendered **"Let's set up your first child"**, the exact same empty state a genuine brand-new zero-children account sees, instead of bouncing to `/login`. Read the actual code to confirm the root cause (not just the live symptom): `dashboard/page.tsx:123` calls `const parentId = await currentParentId();` — `currentParentId()` in `repo.ts` (line 217) DOES do a live `findParentById` lookup and DOES check `token_version`, correctly returning `null` for a deleted parent or an invalidated ("sign out everywhere") session — but `dashboard/page.tsx` never checks `parentId` for `null` before falling through to `kids = parentId ? await listChildren(parentId) : []` and rendering the zero-children branch. Confirmed by contrast that this is an ISOLATED miss, not a site-wide pattern: `schedule/page.tsx:33-34` and `settings/page.tsx:70-71` both correctly do `if (!parentId) redirect("/login?redirect=/...")` right after the same `currentParentId()` call — `dashboard/page.tsx` is the one page that skips this check, and it is the single highest-traffic, first-hit page in the app.
  - Root cause: missing `if (!parentId) redirect("/login?redirect=/dashboard");` guard in `dashboard/page.tsx`, present in every sibling page that reads `currentParentId()`.
  - Fix: add the same one-line guard used by `schedule/page.tsx` / `settings/page.tsx`, right after line 123, before the `parent?.full_name` greeting logic (which would otherwise also read confusingly for a null parent).
  - Risk: Low — one-line addition matching an already-proven pattern used on two sibling pages. Worth a live re-check: log in as SMOKE, bump `token_version` (or simulate via a soon-to-expire manual test), confirm `/dashboard` now redirects to `/login?redirect=/dashboard` instead of showing the onboarding empty state. Note the real-world trigger for this isn't just deletion — it is also the documented "sign out everywhere" / password-change security feature (`token_version` bump), so a user who deliberately invalidates another device's session to protect their account would currently see that other device silently keep "working" (an empty, harmless-looking dashboard) rather than being kicked to sign back in — undermining the clarity of that security feature, even though no other family's data is ever exposed (the data-silo itself holds; this is a confusing-state bug, not a data leak).
