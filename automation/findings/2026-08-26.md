- [x] **B1 · High · A mock-exam question pulled from the practice/mastery pool loses its actual content when the question type is `fill_blank` — the child sees only a generic instruction with no equation, no context, and four answer options with nothing to reason from** — `src/lib/db/repo.ts:1890-1901` (`buildMockPaper`)
  - Repro / evidence: certified `maths_sequences` this run to unlock the Maths mock (9/10 → 10/10 certified), then took the full 10-question Maths mock end to end. Question **7 of 10** rendered as: heading *"Solve the equation by filling in the answer."* with four buttons `x = 3` / `x = 4` / `x = 5` / `x = 6` and **no equation shown anywhere on the screen**. Screenshot: `.playwright-mcp/mock-fillblank-q7.png`. The only reason I could answer it correctly is that I had solved the *exact same authored question* ("2x + 3 = 11, so x = ") minutes earlier in the `maths_algebra_linear` lesson itself, in this same session — a real child sitting a mock cold has no way to know what equation is being asked about. This is Foundation-tier, Non-calculator paper framing (correct exam-condition fidelity elsewhere), which makes the one broken question stand out even more.
  - Root cause: confirmed by reading the seed data directly. The authored `SeedQuestion` for this item (`src/lib/data/curriculum.seed.interactive.ts:20-38`) is:
    ```
    prompt: "Solve the equation by filling in the answer.",
    options: ["x = 3", "x = 4", "x = 5", "x = 6"],
    correct_index: 1,
    interaction: {
      type: "fill_blank",
      parts: ["2x + 3 = 11,  so  x = ", ""],
      blanks: [{ answers: ["4"], numeric: true, placeholder: "?" }],
    },
    ```
    The real question text ("2x + 3 = 11, so x = ___") lives ONLY in `interaction.parts`, by deliberate design (the child-facing lesson UI renders the interaction, not the raw `prompt`, exactly per the doc comment on `QuestionDoc.interaction` in `src/lib/db/types.ts:457-463`). But `buildMockPaper` (`repo.ts:1890-1901`) maps a `QuestionDoc` to a `MockQuestion` using only `q.prompt`, `q.options`, `q.correct_index`, `q.explanation` — it never reads or forwards `q.interaction` — and `MockExamPlayer`/`mock-exam-player.tsx` only ever renders `q.prompt` as the heading (grepped the whole file: zero references to `interaction`). Compare with the OTHER interactive question type in the same mock (question 3, a `drag_drop` "Match each shape to its number of sides" item): that one degrades fine, but only because its author happened to ALSO write a fully self-contained top-level `prompt` + `options` ("Triangle = 3, Square = 4, Pentagon = 5" as one option) as a redundant MCQ fallback — the `fill_blank` item's author did not, since the convention for `fill_blank` is that `prompt` is a generic wrapper (this is confirmed consistent: `qCol.find` in `buildMockPaper` filters `kind: ["practice","mastery"]` with no interaction-awareness at all, so ANY future `fill_blank` item authored the same idiomatic way will hit the identical bug). The diagnostic pool is unaffected (no `kind: "diagnostic"` question in the codebase currently uses `interaction`).
  - Fix: in `buildMockPaper`, when mapping a question whose `normalizeInteraction(q.interaction)` (already exported from `src/lib/child/interactions.ts`, safe/legacy-tolerant) resolves to `type: "fill_blank"`, synthesize a self-contained display prompt by joining `interaction.parts` with the blank rendered as a literal placeholder (e.g. `parts.join("___")` → `"2x + 3 = 11,  so  x = ___"`) instead of using the raw generic `q.prompt`. This requires no new field on `MockQuestion` — just a smarter `prompt` value at build time — so it is a small, contained, low-risk change. Add a unit test asserting the exact seeded "2x + 3 = 11" item produces a `prompt` containing the substring `"2x + 3 = 11"` when run through the new mapping.
  - Risk: low — purely additive display-text logic gated on an already-safe normaliser; every other question kind (`mcq` via absent/invalid `interaction`, and any `drag_drop`/`tap_reveal` item whose authored top-level prompt is ALREADY self-contained, as both examples found this run are) is completely untouched. Worth a companion note for future curriculum authoring (not a code change): when writing a NEW `fill_blank`/`tap_reveal`/`drag_drop` question, either give it a self-contained top-level `prompt`/`options` pair (as `maths_geometry`'s drag_drop item does) or rely on this fix to synthesize one for `fill_blank` specifically — `tap_reveal`/`drag_drop` items should still be spot-checked for the same "generic wrapper prompt" trap during any future authoring pass.

- [ ] **B2 · High · AI tutor explanations can leak raw LaTeX delimiters (`\( \)`, `\times`) verbatim into a child-facing answer, because nothing in the codebase renders LaTeX and the "explain a wrong answer" system prompt never tells the model to avoid it** — `src/lib/ai/teaching-agent.ts:135-141` (`generateExplanation`'s system prompt)
  - Repro / evidence: as Ivy, in the `maths_algebra_linear` lesson, answered *"If x = 4, what is 3x − 5?"* incorrectly on purpose, then tapped **"Why isn't that right?"**. The Checker-PASSED explanation (`aiVerified: true`) rendered as: *"Let's go through it together. If \( x = 4 \), we substitute 4 into the equation \( 3x - 5 \). So, it becomes \( 3(4) - 5 \). First, calculate \( 3 \times 4 = 12 \)…"* — the literal characters `\(`, `\)` and `\times` are shown to the child as text, not parsed as maths notation. Screenshot: `.playwright-mcp/latex-explanation.png`. Confirmed no math-rendering library exists anywhere in the repo (`grep -r "katex|KaTeX|remark-math|MathJax"` across the whole codebase returns zero files), so any LaTeX the model produces is always shown raw.
  - Root cause: `runTeachingAgent` (called by the ONLY handler in `src/app/api/tutor/route.ts`, which serves both the "Why isn't that right?" distractor-aware explanation and any other free-text tutor explanation) calls `generateExplanation`, whose system prompt (`teaching-agent.ts:135-141`) has no instruction at all about maths notation. Compare with the sibling `generateAnimation` function (`teaching-agent.ts:270-279`, used by the SEPARATE "Explain it my way" agentic-animation feature via `/api/explain-animation`) which explicitly instructs: `'Math syntax inside "expression"/"focus": use ^2 for squared, sqrt(9) for roots, +/- for plus-or-minus, plain ASCII only.'` — live-verified this run that the animation path (which I also triggered, on a different wrong answer) rendered clean ASCII maths ("(n-2) * 180°") with no LaTeX at all, confirming the ASCII-only instruction works and the plain-explanation path is simply missing the equivalent guard. The Teaching Checker (`runChecker`, `teaching-agent.ts:170-194`) only validates factual accuracy and tone — it has no notation/renderability check, so a LaTeX-laden explanation passes it every time the underlying maths is correct (as it was here).
  - Fix: add one line to `generateExplanation`'s system prompt (`teaching-agent.ts:135-141`), matching the wording already proven to work on the animation path: `"Never use LaTeX or markup delimiters (no \\( \\), \\[ \\], $, $$, \\times, \\frac, etc.) — there is no maths-rendering pipeline downstream, so write any maths in plain text using normal symbols (×, ÷, ², √, ±)."` No other code changes needed — this is a prompt-only fix, gated by the same Checker that already runs on every explanation.
  - Risk: very low — purely an instruction addition to an existing prompt; re-verify with a couple of live "why isn't that right?" taps on algebra/geometry questions (the topics most likely to prompt LaTeX-style output from the model) to confirm the explanation now reads with plain symbols, and that the Checker still passes genuinely correct explanations (nothing about the fix changes what's being explained, only how the maths notation is written).
