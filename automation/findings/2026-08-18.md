- [x] **B2 · Medium · mobile overflow regression on the child hub: the "Pick up where you left off" resume card blows past the 390px viewport** — `src/components/child/resume-card.tsx:26,31`
  - Repro / evidence: logged in as Ivy at 390x844, a mid-flow lesson present
    (Maths "Fractions, Decimals & Percentages", step 3 of 4). `document.
    documentElement.scrollWidth` measured 533px against `window.innerWidth`
    390 (143px of horizontal overflow) — the first break of the "no 390px
    overflow anywhere" baseline this loop has confirmed clean for ~15 prior
    runs. Walked the DOM: the `<a>` resume-card link itself rendered
    512.6px wide although its own grid parent (`.mb-5.grid.gap-3`, line 26)
    is only 340px. Root-caused live by patching the element with
    `el.style.minWidth = '0'` via `browser_evaluate`: the link's width
    dropped to exactly 340px and `document.documentElement.scrollWidth`
    dropped to 380 — the same healthy baseline every other page measures,
    confirming the fix and eliminating the overflow entirely.
  - Root cause: `resume-card.tsx:26` wraps the cards in a bare `grid gap-3`
    with NO explicit `grid-cols-N` utility, so the browser falls back to a
    single implicit `auto`-sized column. Unlike Tailwind's numbered
    `grid-cols-N` classes (which set `minmax(0, 1fr)` specifically to avoid
    this), a bare `auto` grid track can grow to the MIN-CONTENT size of its
    item. The card link (line 31) has no `min-w-0` of its own, so its
    min-content — driven by the `truncate` subtitle's full un-wrapped text
    ("Maths · Fractions, Decimals & Percentages · step 3 of 4", which
    `white-space: nowrap` treats as one unbreakable line for min-content
    purposes even though it visually truncates once given a width) — forces
    the grid track, and therefore the whole card, wider than the viewport.
    The nested `min-w-0 flex-1` div on line 36 only fixes the FLEX row's own
    internal shrink; it does nothing for the GRID track sizing one level up.
  - Fix: add `min-w-0` to the `<Link>` className on line 31 (the actual grid
    item), e.g. `"child-touch child-panel group flex min-w-0 items-center
    gap-4 p-5 transition-all hover:scale-[1.01]"`. Verified this exact
    one-class change resolves it live. Secondary note for the same sweep:
    `components/child/quest-cards.tsx:65` (`"relative grid gap-5"`) uses the
    identical bare-`grid` pattern; it hasn't reproduced overflow this run
    because subject-card text is short ("English", "3/10"), but it carries
    the same latent risk if a subject label ever gets longer — worth adding
    `min-w-0` there too as a defensive one-liner in the same commit.
  - Risk: none — `min-w-0` only affects sizing, not layout direction; the
    `truncate` on the subtitle already handles the visual ellipsis once the
    box is correctly constrained.

- [ ] **B3 · Medium · rapid/simultaneous taps drop state in the See-it "Your turn" order-tap recall widget** — `src/components/child/teaching-animation.tsx:1533-1546`
  - Repro / evidence: opened "See it" on a science mastery question (Cell
    Biology, `sci_cells`), advanced to the final beat where the `order_steps`
    "Your turn, [name] — tap the steps in the order they happen" mini-recall
    renders. Dispatched three tap events on the "Start", "Change" and
    "Result" chips back-to-back within a single `browser_evaluate` call
    (`document.querySelectorAll('button')` → `.click()` × 3, no delay
    between them, simulating a fast triple-tap). Result: only the LAST
    click ("Result") registered as tap #1 — "Start" and "Change" were
    silently dropped, and the widget never reached its 3-of-3 completion
    state at all. Confirmed the mechanism is genuinely stateful (not a
    fluke) by then tapping the SAME three chips as three separate,
    naturally-spaced `browser_click` calls: every tap registered correctly
    that time and the calm "That's exactly it — you saw it for yourself."
    confirmation + settle animation fired as designed. So the bug is
    specifically triggered by near-simultaneous input, not normal use.
  - Root cause: `tapOrderItem` (lines 1533-1546) builds the next tapped
    array from the closure variable directly — `const next = [...tapped,
    index]; setTapped(next);` — instead of a functional updater. When two
    or three clicks fire within the same React batch (a fast double/triple
    tap is a realistic touchscreen gesture, especially from an excited
    child), each call's closure captures the SAME pre-batch `tapped` value,
    so only the final call's `next` wins and the earlier taps are lost.
  - Fix: switch to the functional form —
    `setTapped((prev) => (prev.includes(index) ? prev : [...prev, index]))`
    — and move the completion check (`checkYourTurnOrder` + `finish(...)`)
    into a `useEffect` that watches `tapped` and fires once
    `tapped.length === task.items.length`, matching the pattern already
    used elsewhere in this file for wrong-attempt settles. This is the
    exact class of "rapid/double input — nothing should desync" bug this
    loop is asked to test for every run.
  - Risk: low — this is a self-contained, skippable recall widget (a
    "Skip" control always escapes it), not gating lesson progression, so
    the blast radius of a bad fix is small; keep the existing calm
    correct/miss copy and `Celebration` burst untouched, only change how
    `tapped` accumulates.
