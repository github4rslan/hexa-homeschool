- [x] **B1 · High · approving (or editing) one child's weekly plan from the dashboard's per-child deep link silently mutates a DIFFERENT child's plan instead** — `src/app/(dashboard)/schedule/actions.ts:19-25,75-100`
  - Repro / evidence: parent dashboard showed Sam Smoke with "Sam doesn't have
    a plan yet — set up this week in one tap" and a `Generate Sam's week` link
    to `/schedule?child=<Sam's id>` (the active-child cookie at the time
    pointed at Ivy, per the sidebar's "Active child: Ivy Test" pill). Clicked
    the link, the page correctly rendered SAM's proposed week (title, combobox
    and "Approving confirms the week for Sam" copy all say Sam — the page
    resolves the child from the `?child=` query param, per the existing `F7`
    comment in `page.tsx:35-42`). Clicked "Approve this week" — the form
    action POSTed 200. Re-navigated fresh to the same
    `/schedule?child=<Sam's id>` URL: it STILL showed the unapproved
    "Approve this week" button, not the "Approved" badge — direct proof the
    write did not land on Sam's schedule document, even though the page the
    parent was looking at, and had just approved, was unambiguously Sam's.
  - Root cause: `page.tsx` resolves the child to render from
    `childParam ?? readActiveChildId()` (query param wins), but the shared
    `activeChildId()` helper in `actions.ts` (used by `approveSchedule`,
    `swapTopic`, `moveDay`, `clearDay` and `regenerateWeek` — ALL five
    schedule-mutating actions) only calls
    `getActiveChild(parentId, await readActiveChildId())` — it never reads the
    `child` query param the page itself used to decide what to show. When the
    active-child cookie doesn't match the child the parent is actually
    looking at (exactly the multi-child "deep-link from the dashboard nudge"
    scenario `today-card.tsx` deliberately sets up), every mutating action on
    that page silently targets the WRONG child's document instead of erroring
    or targeting the one on screen. `approveWeeklySchedule` only flips a
    boolean (`{ $set: { approved_by_parent: true } }`), so this specific repro
    was harmless (it just re-set Ivy's already-`true` flag), but the general
    bug is real: a parent believes they reviewed and approved a specific
    child's week, but a different child's plan is what actually got marked
    approved, while the child they were looking at is left silently stuck on
    "Approve this week" forever with no error shown.
  - Fix: thread the resolved child id through the form, matching the pattern
    `page.tsx` already established. Simplest correct change: add a hidden
    `<input type="hidden" name="childId" value={child._id.toHexString()} />`
    to each of the five forms/`<form action=...>` calls in `page.tsx` and
    `editable-schedule.tsx` (wherever `swapTopic`/`moveDay`/`clearDay` are
    invoked), then in `actions.ts` change `activeChildId()` to accept
    `formData` and prefer `formData.get("childId")` (ownership-checked via
    the existing `getActiveChild`/`assertOwnsChild` path) over the cookie,
    falling back to the cookie only when the field is absent. Keep the
    ownership check exactly as-is — this is a "which child" bug, not an
    authorization bug.
  - Risk: low — this only changes which child id the same, already-tested
    repo functions receive; no schema change. Verify the existing schedule
    unit tests (`tests/*schedule*`, if any) still pass, and re-drive this
    exact repro live (dashboard deep-link to a NON-active child, approve,
    reload) to confirm the badge now flips correctly.

- [x] **B3 · Low (accessibility) · mcq radiogroups don't support arrow-key navigation, breaking the standard ARIA radiogroup pattern sitewide** — `src/components/child/interaction.tsx:191-220`
  - Repro / evidence: keyboard-only pass on a live mastery mcq. Tabbed to the
    first `role="radio"` button (confirmed via `document.activeElement`),
    pressed `ArrowDown` — focus did NOT move to the next option (screen
    readers and most users expect Up/Down or Left/Right to cycle radio
    options within a group, per the WAI-ARIA APG radiogroup pattern). Had to
    fall back to `Tab` to reach the next option, which DOES work (each
    `role="radio"` button is independently tabbable, so keyboard reachability
    itself is not broken), but it does not match the interaction a screen
    reader announces ("radio group, 4 items" implies arrow-key cycling) and
    is a real gap for SEND / assistive-tech learners (Ivy has a dyslexia
    indicator; the same `InteractiveStep` mcq renders in every lesson, warm-up
    and mock question sitewide, so this is one fix with wide reach).
  - Root cause: each option renders as an independent
    `<motion.button role="radio" aria-checked={chosen} onClick=...>` inside a
    plain `<div role="radiogroup">` with no roving-`tabIndex` management and
    no `onKeyDown` handler for Arrow keys — the group relies entirely on
    native Tab order rather than implementing the radiogroup keyboard
    contract.
  - Fix: add an `onKeyDown` handler on the `radiogroup` div (or each radio)
    that intercepts `ArrowDown`/`ArrowRight` (move to next option, wrapping)
    and `ArrowUp`/`ArrowLeft` (previous, wrapping), calling the same
    `setSelected(i)` used by `onClick`, and set `tabIndex={chosen || (selected
    === null && i === 0) ? 0 : -1}` on each radio so Tab enters/exits the
    group in one stop (the standard roving-tabindex pattern) rather than
    stepping through all 4 options individually. Keep the existing `onClick`
    path untouched for mouse/touch.
  - Risk: low — purely additive keyboard behaviour; verify Tab still reaches
    the group in one stop and Enter/Space still submits via the existing
    "Check answer" button afterward. Re-run the keyboard-only pass on a live
    mcq post-fix to confirm arrow keys now cycle options and screen-reader
    announcement (`aria-checked`) still flips correctly.
