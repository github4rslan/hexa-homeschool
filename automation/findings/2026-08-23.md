- [ ] **B1 · Critical · The "Topic mastered!" completion screen's own call-to-action buttons render with clipped, partly unreadable text — on EVERY certification, both desktop and mobile** — `src/components/ui/button.tsx:6-90` (`buttonVariants`, `size: child`), used at `src/components/child/practice-player.tsx:1473-1499`
  - Repro / evidence: certified `eng_devices` (desktop 1280px) and separately `maths_geometry` (desktop, then again at mobile 390px) — on the resulting "Topic mastered!" screen, all three CTA buttons ("Save my certificate", "See it on my journey", "Back to subjects") render with their text visibly cut off at both edges: e.g. "Save my certificate" reads "ve my certifica", "See it on my journey" reads "it on my journ", "Back to subjects" reads "ack to subjec". Screenshots: `.playwright-mcp/topic-mastered-viewport.png` (desktop), `.playwright-mcp/topic-mastered-geometry-clip-check.png` (desktop, second topic), `.playwright-mcp/topic-mastered-mobile.png` (mobile — same clipping, confirmed via DOM measurement below). This is the single biggest emotional payoff screen in the whole product (trophy + confetti + "you did it") and its own primary action is illegible.
  - Root cause: confirmed via `getBoundingClientRect`/`scrollWidth` on the live DOM. On **desktop**, the three `size="child"` buttons (`h-20 px-10 text-2xl rounded-3xl`, `whitespace-nowrap`, `overflow-hidden` — `button.tsx:8-17,82`) sit in a `flex flex-row gap-3 justify-center` row (`practice-player.tsx:1473`) whose combined natural content width (~790px+) exceeds the card's available width (~575px); with no `flex-shrink-0` anywhere, the browser's default `flex-shrink: 1` squeezes each button below its own text's natural width (measured: button #1 `clientWidth` 184px vs its own label's `scrollWidth` 258px — a 74px deficit), and because the label is `whitespace-nowrap` + the button is `overflow-hidden`, the un-fitting text is silently clipped rather than wrapping or the button growing. On **mobile**, the container switches to `flex-col` (full width each), yet the SAME clipping still happens (measured: `clientWidth` 275px vs `scrollWidth` 303px for "Save my certificate") — because `text-2xl` + `px-10` simply makes the label wider than the available column width at any viewport; there is no responsive text-size step-down and no permission for the label to wrap to a second line.
  - Fix: two independent, complementary changes, both scoped to the `child` button size so no other button variant/size is touched: (1) allow the `child` size's label to wrap instead of being forced onto one line — override the base `whitespace-nowrap` for this size only (e.g. add `whitespace-normal` and a sensible `min-h-20 h-auto py-4` in the `size.child` string in `buttonVariants` at `button.tsx:82`; because the outer `cn(buttonVariants(...), className)` call already runs `twMerge` — confirmed in `lib/utils.ts:8-10` — a same-property override placed after the base class in the concatenated string is resolved correctly, so this is a safe, already-supported pattern, not a new mechanism); (2) prevent flex-shrink from squeezing these buttons on desktop by adding `shrink-0` alongside a `flex-wrap` on the row container at `practice-player.tsx:1473` so three buttons that don't fit one line wrap to a second line at their natural (now-wrapped-label) size, rather than being compressed. Add a Playwright/DOM regression check post-fix: `button.clientWidth >= 0` is trivially true, so the real assertion is `button.scrollHeight` stays within the button's own rendered height (i.e. no more `clientWidth < scrollWidth` on a single-line label) at both 1280px and 390px.
  - Risk: low-medium — this Button size is used elsewhere in `(child)` routes (e.g. "Start mastery", "Keep going", "Finish"), so re-check every child-size button after the change: those all have SHORT single-word/two-word labels today so they're very unlikely to newly wrap, but take a screenshot of each after the fix to confirm no regression (i.e. confirm they don't ALSO start wrapping unnecessarily at their natural width).

- [ ] **B2 · High · A Science-adjacent "letter tiles" English visual renders on a multi-example onomatopoeia mastery question, misleadingly spelling out the FIRST quoted word with no connection to the actual question** — `src/lib/child/english-visual.ts:86-97` (`deriveEnglishVisual`, the quoted-word `letter_tiles` branch)
  - Repro / evidence: as Ivy (`eng_devices`, Language Devices), the mastery question **"'Buzz', 'crash' and 'splash' are examples of:"** (correct answer: Onomatopoeia, index 2) rendered a derived figure with alt text **"The word 'buzz' shown as individual letter tiles."**, visually spelling out b-u-z-z as four separate tiles. The question is asking the child to identify the literary device that all THREE examples share — the figure instead singles out only the first one and displays it as a generic spelling/word-building visual (the same visual kind used elsewhere for "what's the opposite of 'begin'?"-style single-word vocabulary questions), which has no relationship to "these three words all imitate sounds" and could actively mislead a child into thinking the question is about spelling "buzz", not about onomatopoeia. Screenshot: `.playwright-mcp/english-visual-wrong-letter-tiles.png`. Confirmed live by answering the question correctly and observing the figure throughout.
  - Root cause: `deriveEnglishVisual`'s `letter_tiles` regex (`english-visual.ts:89`, `` `${Q}([a-z][a-z]{2,})${Q}` ``) matches the FIRST single quoted word anywhere in the prompt with no check for how many quoted words the prompt contains. The comment directly above it (`english-visual.ts:87-88`) already anticipates one failure mode ("a quoted SENTENCE never triggers a misleading figure") but does not anticipate this one: a prompt with **multiple separate quoted single words** (a list-of-examples question, here three: 'Buzz', 'crash', 'splash') is a different shape entirely — it's asking about a shared PROPERTY of several words, not featuring one specific word to spell out — yet the regex still fires on the first match.
  - Fix: add a guard so `letter_tiles` only fires when the prompt contains **exactly one** quoted single word (not two or more) — e.g. count all matches of the same quoted-word regex globally first, and return `null` from this branch when the count is anything other than 1. This directly extends the existing "no misleading figure over a shape we're not confident about" philosophy already used one branch up. Add a unit test asserting `deriveEnglishVisual("eng_devices", "'Buzz', 'crash' and 'splash' are examples of:")` returns `null`, alongside the existing single-quoted-word passing cases.
  - Risk: low — the fix only makes the `letter_tiles` branch MORE conservative (strictly fewer matches), so a genuinely single-word prompt is unaffected and multi-word-list prompts safely fall through to the generic AI-image fallback instead of a wrong figure. Re-run the `english-visual` test suite to confirm no currently-passing single-word prompt (e.g. "the opposite of 'begin'") regresses to `null`.

- [ ] **B4 · Low · The dashboard's date/day-of-week header is computed in server UTC, not UK time, so it can show the wrong date/weekday to a parent near the midnight BST/GMT boundary** — `src/components/dashboard/topbar.tsx:8-12`

  - Root cause: `topbar.tsx:8` calls `new Date().toLocaleDateString("en-GB", { weekday: "long", day: "numeric", month: "long" })` with **no `timeZone` option**. The portfolio generator (`lib/compliance/portfolio.ts`, per its own "BST"-labelled output) already does this correctly elsewhere in the codebase; the topbar just never adopted the same pattern.
  - Fix: add `timeZone: "Europe/London"` to the `toLocaleDateString` options at `topbar.tsx:8-12` (one-line change, matches the fix pattern the memory log already used for a comparable hydration/date issue elsewhere in this codebase — pin the IANA zone explicitly rather than relying on the runtime's default).
  - Risk: very low — presentational only, no logic depends on this displayed string; verify the string still renders correctly (no `Invalid Date` / no hydration mismatch, since the value only differs by an hour of drift at the exact BST boundary, not across a client/server render split).
