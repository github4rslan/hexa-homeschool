# Bug Audit — Systematic Findings (read-only)

**Scope:** whole Edway codebase, with the owner-flagged **voice / narration** bug
root-caused first. Generated by the `bug-hunt` task. **No code was changed and
nothing was committed** — this is a findings report only; `bug-fix.md` applies fixes.

**Method:** static trace of the child lesson flow, narration engine, the recent
Wave-7 seams (parent-events, remediation handoff, adaptive feedback), the
child-facing API routes, and the repo-layer ownership checks. Reproduction on
edway.uk was **not** run — every child/parent surface here is auth-gated, so the
findings are traced from source (marked *needs test fixture* where a live repro
would add value).

## Severity ranking

Critical = breaks child-safety, security/data-silo, or the core learning loop.
**No Critical (invariant-violating) defect was found** — the Teaching-Checker
gate, the distress-gate ordering in `/api/tutor` + `/api/stt`, and the
`repo.ts` ownership checks all hold on the paths reviewed. The highest-impact
issues are the two **High** narration defects the owner reported.

## High

### N1 · High · Voice/narration · Two `useNarration` instances play at once (overlap)
**File:** `src/components/child/practice-player.tsx:314-321` (feedback narration)
and `src/components/child/practice-player.tsx:1223-1244` (mounts `<StepReveal>`),
against `src/components/child/step-reveal.tsx:45` + `:58-64` (StepReveal's own
`useNarration` + its auto-play effect).

**Repro/trigger:** In practice, answer a question **wrong** in a way the adaptive
matrix classifies as a concept gap (or exhaust attempts on the final try). In
`check()` two things fire in the same render:
1. `setFeedback(decision)` → the effect at `practice-player.tsx:314` calls
   `narration.playText(spoken)` on **PracticePlayer's** audio element (voice #1),
   speaking the matrix line + misconception.
2. `decision.escalateReteach` → `setStepByStepOpen(true)` (`:578`) →
   `<StepReveal>` mounts (`:1232`) → its effect (`step-reveal.tsx:58`) calls
   `narration.playText(currentNarration)` on **StepReveal's own** audio element
   (voice #2), reading step 1 of the worked example.

**Root cause:** `useNarration` creates a *private* `<audio>` element per hook
instance (`use-narration.ts:44`, `getAudio()` at `:54`). PracticePlayer and the
StepReveal it renders each own a separate instance with no shared coordination,
so "one clip at a time" is only enforced *within* an instance, never *across*
them. Whenever a component that owns narration renders a child that also owns
narration, both can play simultaneously → **two overlapping voices**. (The
explainer→practice transition is safe because `DailyFlow` uses
`AnimatePresence mode="wait"`, so those two instances are never mounted together;
the practice-player↔step-reveal pair is not protected that way.)

**Suggested fix:** Introduce a single shared audio controller — one `<audio>`
owned by a `NarrationProvider`/context at the lesson root, with `useNarration`
becoming a thin consumer of it. StepReveal then shares the same element and a new
play automatically stops the previous, killing the overlap. (Combine with N2's
play-token so the shared element can't be double-driven.)

**Risk of fixing:** Medium. Touches every narration consumer (explainer,
step-reveal, practice-player, my-stuff preview). Needs care that unmount cleanup
(URL revocation, `use-narration.ts:163-170`) moves to the provider so object URLs
aren't revoked while another consumer still needs them.

### N2 · High · State/race · No play-token guard in `playText` → narration resumes after `stop()` and clips truncate
**File:** `src/lib/child/use-narration.ts:107-129` (`playText`), interacting with
`:102-105` (`stop`) and `src/components/child/practice-player.tsx:799-803`
(`onAnswerStart`).

**Repro/trigger:**
- *Plays over the working child:* A step appears → auto-narrate effect
  (`practice-player.tsx:270-277`) calls `playText`, which `await`s `fetchUrl`
  (a network round-trip on a cache miss). During that await the child taps an
  answer → `onPointerDownCapture` → `onAnswerStart` → `narration.stop()`
  (`:802`). `stop()` only pauses the (not-yet-playing) element; then `playText`
  resolves and unconditionally calls `a.play()` (`use-narration.ts:122`), so
  narration starts **after** the child began answering. Because
  `silencedStepRef.current === step` is now set, subsequent taps won't stop it
  again — the voice keeps talking over the child until the next step.
- *Clips cut each other off:* Two `playText` calls that resolve out of order both
  run `a.pause(); a.src = url; a.play()` on the same element with no ordering
  guard, so the later-resolving fetch wins and truncates whatever was playing —
  perceived as narration "cutting out".

**Root cause:** `playText` captures no generation/token before its async
`fetchUrl`, and never re-checks whether it was superseded (by a newer `playText`)
or cancelled (by `stop()`) before calling `a.play()`. `stop()` sets no "cancelled"
state that a pending `playText` can observe.

**Suggested fix:** Add a monotonic `playTokenRef`. `playText` increments it and
captures the value before `fetchUrl`; after the await, bail if the captured token
!= current. `stop()` also bumps the token (marking any in-flight play stale). This
is exactly the "play-token guard" the task calls for; pairs naturally with N1's
shared controller.

**Risk of fixing:** Low. Localised to `use-narration.ts`; the public API
(`NarrationApi`) is unchanged.

## Medium

### A1 · Medium · Recent-wave seam · Parent activity feed is written but never displayed
**File:** `src/lib/db/repo.ts:3523` (`listActivityFeed`, defined) — **zero
callers** anywhere in `src/` (verified by grep). Events are produced by
`emitMasteryEvent` / `recordHandoffEvent` / `emitInactivityEvent`
(`src/lib/notify/parent-event.ts`) and stored in `parent_events`, but nothing
reads them back into a UI.

**Repro/trigger:** Certify a topic or trigger a handoff → a `parent_events` row is
written and the mastery email/SMS fires, but no dashboard surface shows the feed.
The Settings copy added in this change
(`src/app/(dashboard)/settings/page.tsx:227-231`) tells the parent milestone
events are "Always shown on your dashboard feed regardless" of the email opt-out —
**that feed does not exist in the UI**, so the claim is currently false.

**Root cause:** Wave-7 Phase-5 shipped the write path + cron + email templates and
the read helper (`listActivityFeed`), but the dashboard render that consumes
`listActivityFeed` was not wired in (the dashboard still uses its pre-existing
activity rendering, which does not query `parent_events`).

**Suggested fix:** Either mount `listActivityFeed` in the dashboard activity
section, or soften the Settings copy until the feed ships. Prefer wiring the feed —
it's the justification for making the email opt-out safe.

**Risk of fixing:** Low. `listActivityFeed` is already ownership-scoped and
read-only; wiring it is additive.

### S1 · Medium · Child-safety · `fill_blank` distress scan is fire-and-forget and swallows network errors
**File:** `src/components/child/practice-player.tsx:521` (`void guardFreeText()`)
and `:490-511` (`guardFreeText`).

**Repro/trigger:** In a `fill_blank` question, type a distress phrase and tap
"Check answer". `check()` fires `void guardFreeText()` (not awaited) and proceeds
to show feedback and allow "Keep going". The freeze **does** still fire when the
`/api/safety-check` response resolves (`setFrozen` replaces the whole UI), but:
(a) feedback/advance can occur before the scan returns, and (b) if the
`/api/safety-check` fetch **throws** (network error), the `catch` at `:507`
returns `false` with the comment "never block on a network error" — so a real
distress phrase is silently **not** frozen.

**Root cause:** Deliberate "instant feedback" design made the typed-answer distress
scan non-blocking and best-effort-on-error. That conflicts with the child-safety
principle "over-triggering is acceptable; missing real distress is not" for the
one free-text child surface. (The graded `/api/tutor` path and `/api/stt` both
scan synchronously and short-circuit, so this gap is specific to `fill_blank`
practice answers.)

**Suggested fix:** Await `guardFreeText()` before revealing feedback/enabling
advance for `fill_blank`, and on a network error **fail safe** (freeze/pause and
retry) rather than continuing. If instant feedback must be kept, at minimum block
the "Keep going" button until the scan resolves.

**Risk of fixing:** Low–Medium. Adds a small latency to `fill_blank` feedback only;
must preserve the calm pause UX and not double-escalate.

## Low

### E1 · Low · Error handling · Mastery-reteach freeze path leaves narration playing
**File:** `src/components/child/practice-player.tsx:657-660` (`runReteach`, frozen
branch) vs. the consistent pattern elsewhere (`:418-422` STT, `:501-505`
guardFreeText, `:710-713` fetchInlineReteach all call `narration.stop()` before
`setFrozen`).

**Root cause:** The `runReteach` frozen branch calls `setFrozen(...)` but not
`narration.stop()`. If a distress phrase surfaces via the mastery-reteach
`/api/tutor` call, the calm pause renders while the question narration audio keeps
playing — the pause should be silent.

**Suggested fix:** Call `narration.stop()` (and `stopRecorder()`) before
`setFrozen` in `runReteach`, matching the other three freeze paths.

**Risk of fixing:** Negligible.

### U1 · Low · Child UX / navigation · "Resting" quest card looks actionable but dead-ends
**File:** `src/components/child/quest-cards.tsx:75-130` (the card is a `<Link>`
with a trailing `ArrowRight`, even when `q.resting`), routing to
`src/app/(child)/learn/lesson/page.tsx:63-68` which renders `HandoffPause`
(variant `resting`) whose only action is "Back to my subjects" → `/learn`.

**Repro/trigger:** On the hub, a resting topic shows an inviting card with a
forward arrow. Tapping it navigates into the lesson only to be told "nothing to do
here right now" and sent straight back — a small circular dead-end for a
7–10-year-old.

**Suggested fix:** Render the resting card as non-navigable (no arrow / not a
link), or make the tap a soft in-place explainer instead of a round trip.

**Risk of fixing:** Low.

### V1 · Low · Accessibility · AI question visual can crop meaningful content
**File:** `src/components/child/practice-player.tsx:1076-1082` — the checked
question image renders with `aspect-[3/2] object-cover`.

**Root cause:** `object-cover` crops to fill a fixed 3:2 box. A generated diagram
whose relevant detail sits near an edge can be partially cut off, undermining the
very relevance the Visual Checker approved.

**Suggested fix:** Use `object-contain` (letterbox) for diagram-style visuals so
nothing is clipped, or generate/store at the display aspect ratio.

**Risk of fixing:** Low (visual-only).

### H1 · Low · Data honesty · Mastery "attempts it took" over-counts
**File:** `src/lib/db/repo.ts` `masteryAttemptCount` (counts all `status:
"completed"` lesson logs for the topic) feeding
`src/lib/engine/parent-events.ts:63-73` ("first try" / "N attempts").

**Root cause:** The count includes any prior completed run of the topic (e.g. a
training-level completion, or a spaced-repetition re-run), so the celebration can
say "3 attempts" when certification itself was clean. Minor honesty drift; the
copy claims "no hints on the final set" which is generally true but the attempt
figure isn't strictly "attempts to certify".

**Suggested fix:** Count only attempts within the current certification cycle
(e.g. logs since the last non-certified state), or reword to "practised N times".

**Risk of fixing:** Low.

## Areas checked that held up (no defect)

- **Data-silo / ownership:** the new Wave-7 repo functions
  (`recordParentEvent`, `listActivityFeed`, `inactivityNudgeChildren`,
  `masteryAttemptCount`) are parent/child-scoped; `recordParentEvent` calls
  `assertOwnsChild` before writing, and the feed/nudge queries are constrained to
  the parent's own child ids. No `getCollection` bypass in route handlers found on
  the reviewed paths.
- **Distress-gate ordering:** `/api/safety-check` runs `checkDistress()` *before*
  the rate-limit (`safety-check/route.ts:49-51`), and `/api/tutor` + `/api/stt`
  keep the gate first. Good.
- **Idempotency:** `parent_events` has a unique `(parent_id, dedupe_key)` index
  (`scripts/seed.ts`), and `recordParentEvent` returns `created` from
  `upsertedCount`, so exactly one email/SMS per moment. The inactivity cron
  (`/api/notify/inactivity`) is `CRON_SECRET`-gated and best-effort.
- **`todayCard.allDone`** correctly requires `quests.length > 0`
  (`repo.ts:1378`), so an all-resting day can't misfire the daily-summary email.
- **Rate-limit + auth** present on `/api/tts`, `/api/safety-check`,
  `/api/question-visual` (all require `currentParentId` and call `rateLimit`).
